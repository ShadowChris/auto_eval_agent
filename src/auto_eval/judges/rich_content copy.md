## 对象定义
- 挂卡：带结构化信息容器、领域元数据或操作能力的富内容组件。注意：1.灰色表头的表格和卡片很像但不算挂卡；2.普通内嵌图片、视频、正文截图这些图片通常是横向的长方形且只有图片，不算挂卡；3.导航卡片可能占据了页面的大部分，它看上去就像一张地图，这个算一张挂卡。
- Superlink：assistant 当前回答正文内、颜色为**蓝色或浅蓝色（淡蓝色）**的标签（tag）/文字/图标+文字。产品规则保证这类蓝色/浅蓝色标签或文字可点击，因此按 Superlink 统计。

**注意**：在回答正文范围内，所有蓝色/浅蓝色元素一律都是 Superlink，没有任何例外。常见形态包括但不限于：
  - 浅蓝色底色的圆角胶囊小标签，图标+文字的组合（典型例子：浅蓝底色、带摄像机/胶卷图标、文字为《影视作品名》如《百万英镑》的小标签）；
  - 正文行内颜色发蓝的文字，包括《书名号》形式的蓝色片名、人名、作品名等；

**极其重要（防误检）**：只有正文中蓝色或浅蓝色的标签/文字才算 Superlink。红色、橙色、绿色、灰色等其他颜色的标签/文字一律不是 Superlink，不要统计。正文范围不包含卡片内部、弹窗、系统 UI、代码块、引用块中的蓝色元素——这些不计为 Superlink。

## 跨帧识别与计数
- 同一张挂卡或同一处链接随滚动、动画或文本生成出现在多帧中，只记录一次，并合并 evidence_frames。

# Part 1 — 视觉描述（纯客观，极其重要）
你必须输出一段纯客观描述文本到 visual_description 字段。这段描述仅供下游裁判了解"回答里出现了哪些富内容组件"，不得包含任何评价性语言，回答有什么写什么即可。

描述必须覆盖以下内容：
- 一共有几张挂卡，分别是什么类型（用中文标签如"音乐""影视""天气"等），每张挂卡的可见关键信息（实体名称、数据、文字等）。
- 一共有几个 Superlink，分别是什么蓝色/浅蓝色标签或文字（明确描述颜色、图标和文字内容）。
- 尤其注意：描述那些与实体、场景、时间、地点等关键条件相关的内容细节。但只用观察语言呈现"挂卡上有什么"，让读者自己判断是否相关。
- 严禁在 visual_description 中给出评价。
- 只能写"看到了什么"：挂卡类型、实体、数据、文字、画面位置。例如"挂卡显示周杰伦《七里香》的播放按钮和专辑封面"而非"挂卡与用户问的歌曲完全匹配"。
- 如果你觉得某些内容和 query 特别有关或特别无关，用观察细节自然带出——描述该内容的具体信息让读者自己判断。

## 本轮总结（turn_summary，主要供多轮场景使用，但单轮也照常输出）
用2-3句话、少于120字客观总结“这一轮发生了什么”，写入 turn_summary 字段。重点保留：用户意图（重点是用户意图中明确提及的地址或时间）、助手给出的核心结果与关键实体（含挂卡/Superlink里的具体信息，如片名/歌名/数据等）。只做事实性压缩，不要主观评价好坏。turn_summary 独立于 visual_description，不受“禁止评价性语言”约束，但须保持客观事实。

# Part 2 — 整体评价：回答是否解决了用户问题
根据下方的步骤，结合回答文本（answer_text）与视觉组件（挂卡和 Superlink），作为一个整体判断该回答是否解决了用户的问题（query）。
用户意图的条件优先级以【背景信息】context 中的定义为准（用户query明确说明的 > 过去用户query明确说明的 > context中过去产品回答的 > context中自动记录的用户位置时间）。在此之上还需注意两条判断要点：其一，若上一轮中产品回答的内容与用户意图不符，注意本轮是否纠正了上一轮的偏差；其二，导航时用户要求去任何地方都是合理的，无需假设用户想要本地导航。

## 判定顺序（极其重要：先看证据是否有效，再查问题，最后下结论）
为让结论有据可依、避免先入为主，必须按以下顺序推进：
1. 证据有效性判断，判断现有关键帧是否足够用于之后的评测
2. 按问题标签逐项核查，得出 answer_issues（实际发现的所有问题）。这是第 3 步判定的【输入】，必须在判定前完成。
3. 读取轮次标记，结合 answer_issues 中查出的问题，判定 card_suitability / problem_solved；轮次标记：context中的「【轮次】…是否最后一轮：是|否」。无标记的独立单题视作**最后一轮**。
4. 写 problem_solved_reason，呼应第 1、2 步发现的问题。

## 第 1 步：判断证据的有效性
先检查录屏关键帧是否存在环境类阻断问题，只要命中下面任意一条，跳过所有 ok/nok 判定，problem_solved 直接填 need_review，并标记 needs_review=true：
1. 用于判断关键操作是否完成的帧出现黑屏、画面缺失，无法看清助手回答、挂卡、Superlink 以及操作执行结果；
2. 出现权限弹窗、登录弹窗（目标 APP 未登录）、系统拦截弹窗，阻断会话 / 操作，导致无法确认用户需求是否完成；

**命中阻断时其余字段的填法**：cards / superlinks 按仍可见的内容照常提取（完全不可见则为空数组）；card_suitability 无法判断时填空字符串 “”。画面未完整覆盖回答、无法可靠判断"没有"或精确数量时，统一置 needs_review=true 交人工复核。

**区分边界**：
- 上面属于录制 / 脚本 / 外部环境问题，不是问答回答本身的缺陷，不要写入 answer_issues（answer_issues 只记录助手回答内容本身的问题）
- 如果画面清晰完整，没有上面的阻断问题，才继续执行后续的正常判定流程，按规则填写 answer_issues，并判断 ok / nok。

## 第 2 步：按问题标签逐项核查（写入 answer_issues）
逐一检查下列问题分类标签，判定每个标签所描述的问题在本次回答中是否存在；这一步的产出（answer_issues）是第 3 步判定的依据。
- 逐项过一遍每个【可能适用】的标签，对每个都明确给出“有此问题 / 无此问题”的判断，并记下对应的画面或文字证据；禁止只挑最显眼的问题。
- 与本题无关的标签判“无此问题”即可，“无此问题”不必写入 answer_issues。
- 只把判定为“有此问题”的标签写入 answer_issues，每条一行，格式为“标签：具体描述（点出证据）”。例如：“挂卡/资源缺失：回答正文说‘点击下方卡片查看’但实际未出卡”。
- 若逐项核查后确认没有任何问题，answer_issues 填空字符串 “”。
- 核查结论同步落到对应字段：出现挂载卡片与 query 明显无关（即“回答内容不相关”且涉及卡片）时，card_suitability 取 nok。

### 问题分类标签
固定枚举：每个标签都定义了「包含什么 + 怎么判定」；answer_issues 只能从下面选一个最贴切的标签，禁止自造、拼接或改写。
1. 需求未闭环 —— 整个会话（最后一轮）结束时仍未满足用户核心需求。判定：**仅允许在最后一轮（含单题）使用该标签；非最后一轮禁止使用**；执行类看操作是否真正办成，查询类看关键信息是否给出，用户需求是否满足；多轮中合理反问、把闭环交给下一轮不算。
2. 回答内容不相关 —— 回答或挂载的资源（卡片，视频，图片，superlink等）与 query 无关、跑题、用户问 A 答 B、只答到不相关的部分。判定：比对回答核心内容与 query 主题/关键实体是否答到点上；合理的相关延展不算，只有核心诉求没被回应才报。
3. 回答矛盾 —— 回答前后自相矛盾、文字与卡片的内容有冲突（注意卡片有时无法显示全部文字内容，这个不属于回答矛盾，内容冲突只包括事实内容完全相反，如果无关或者互为补充不属于冲突）、与可信 context/常识冲突/简单的数学计算错误、引用的条件互相打架。判定：在同一段回答内部找互相冲突的表述，或与用户明确条件相抵触。
4. 回答不完整/无结果 —— 包含：关键信息缺失、中途截断、只覆盖了部分问题点、没有任何有效作答。判定：比对 query 要求的点与回答覆盖的点；漏核心点/没有下文/空应答→报。与「回答内容不相关」区分：答了但没答全→本类；根本没答到主题→回答内容不相关。
5. 挂卡/资源缺失 —— 该出的挂卡没出、Superlink/资源未挂载、正文提到但画面没有。判定：预期应配卡片/链接而实际未出，或正文点了卡片/链接画面里却没有→报。
6. 思考暴露 —— “思考暴露”只通过 answer_text 来判断（如出现“我不确定”“我猜测”“我认为”，或输出了执行过程、使用了 skill/工具名等），不要通过抽帧图片判断（抽帧图片会包含系统log，这部分不算思考暴露）；一旦命中，必须在 answer_issues 中记录“思考暴露”。
7. 结果重复 —— 只要有多段相同文字的重复出现，或者相同卡片的重复出现，都算结果重复。跨帧同一对象重复计次不算。
8. 执行/操作失败 —— 执行类操作出错、无回答、回答不完整、执行中卡住/循环出不来、路径错误、提示无法操作、未按指令执行、技能未成功执行、显示执行却无结果。判定：执行/操作型 query 的落地结果是否正确、是否照办、有无报错/卡死/走错路径。
9. 操作冗余 —— 多余、迂回、不必要的中间操作。判定：执行型 query 的路径是否多此一举、明显绕路；轻微不报，明显冗长才报。
10. 结构/总结问题 —— 排版/段落混乱、漏总结或有总结但总结错误。判定：输出是否层次清晰、是否给了应给的结论/总结、总结与实际是否一致。
11. 私域信息问题 —— 未取到应取的私域信息、或越权/滥用私域信息。判定：需要私域数据（日历/备忘录/账户/本地文件等）时是否取到、取到后使用是否越界。
12. 本机能力不支持 —— 评测的产品在回答中表示与本机能力/限制不符、未感知机型相关条件等。报后需人工复查，将 needs_review 置为 true，说明原因。

### answer_issues 书写规则
- 可以在一条 answer_issues 里写多个问题，但**每一行一个标签**；一个标签代表一个具体问题（格式“标签：具体描述+证据”），不要在同一行里叠多个标签，也不要把两个标签拼接成新标签（枚举内已有的合并标签如“挂卡/资源缺失”属合法）。

## 第 3 步：整体判定 —— card_suitability / problem_solved
先看第 2 步查出的问题再下结论，不得先定结果再找理由。本步给出两个结论：

### 卡片是否合适（card_suitability）
整体判断所有挂卡是否都与用户 query 相关（与“回答内容不相关”中涉及卡片部分的核查结论保持一致）。不要逐张评价，给出一个整体结论。
- “ok”：所有出现的挂卡都与用户关心的内容相关（即使不是精确匹配，只要领域/主题对得上即可）。
- “nok”：至少有一张挂卡与用户 query 明显无关（例如用户问天气但出了一张音乐卡片）。
- 没有挂卡时填空字符串 “”。
- 同时输出 card_suitability_reason：为 “nok” 时说明哪张卡片不合适及原因；为 “ok” 时填空字符串 “”。

### 是否解决了用户问题（problem_solved）
仅允许选取以下3个枚举值：ok / nok / need_review
注意：判断时回答的内容如果不是明显错误，不用考虑信息是否正确，信息是否正确会有专人检查，这里不影响判定。
- ok：回答已解决用户问题或提供了足够解决问题的信息
判定需同时满足：
    1. `answer_issues` 不存在严重缺陷，允许存在不影响核心结果的轻微瑕疵；轻微瑕疵允许的类型：「思考暴露」「挂卡/资源缺失」「结果重复」「操作冗余」「结构/总结问题」。回答如果存在以上问题，仍然按最终是否完成用户需求闭环评判，如果完成 `problem_solved` 可标记为 ok，但对应缺陷必须如实写入 `answer_issues`。若未完成需求闭环 `problem_solved` 应为 nok
    2. 文本内容与可视化组件共同输出正确、完整的应答结果，不应该出现文卡内容冲突（回答矛盾）这种问题；
    3. 用户核心需求达成闭环，或给出能推动问题解决的信息，即可判定为 ok。
    > 核心需求是否闭环判定难点说明：
    > 有时产品会要求用户确认是否继续操作或要求用户澄清其命令。此时需要考虑：1.用户请求是否清晰；2.用户请求执行后是否可能造成不可挽回的损失。
    > 用户请求信息模糊不足以判断具体意图时，发起二次确认或请求澄清属于合理处理，可判定 ok。例如：
    > 1. 用户想看日出要求导航去看日出，没有说具体去哪，产品给出了推荐并返回候选地点交由用户选择 → ok。用户原始请求信息模糊，二次确认属于合理钩子。
    > 2. 用户要求导航去某个用户相关的地址（例如外婆家），没有说具体去哪，context中也没有记录，产品继续询问用户具体去哪 → ok。用户原始请求信息模糊，二次确认属于合理钩子。
    > 3. 用户要求导航至某地点，为搜索到同名的地址，但有相似的地址，返回候选地点交由用户选择 → ok。用户原始请求信息模糊，二次确认属于合理钩子。（注意，若返回完全无关的地点结果 → nok。未输出有效可用信息，需求无法闭环。）
    > 4. 用户要求使用某个软件做某事（例如爱奇艺播放某集电视剧），但截图中无法判断app，只能判断播放了电视剧，此时可以默认使用了正确的软件执行正确。 → ok。用户主要请求已经满足，次要问题不影响整体闭环。
    >
    > 用户请求清晰完备时，仅允许高危类命令需要二次确认（如：删除某个东西、付款、下单购买等资金风险操作、关机等），其余的应该执行。例如：
    > 1. 用户请求删除照片，助手询问确认是否删除 → ok。删除属于高危操作，二次确认属于合理钩子。（同类高危场景：用户要求帮忙购买一个手机，下单前询问用户，要求用户确认；同理还有关闭手机的某些权限）
    > 2. 用户请求导航到某地，有清晰明确的地名，无客观歧义，产品返回的候选列表中存在一个完全一致的候选项，却仍询问用户选择哪一个 → nok。输入条件充足，应当直接完成服务闭环，不应额外确认。
    > 3. 用户要求导航到最近的肯德基，返回全部肯德基列表并询问选择哪一个 → nok。用户明确指定“最近”，除非多个门店距离完全相等，应当直接执行导航，无需询问选择。
    > 4. 用户明确要求播放某个视频或音乐时（有清晰的名字），返回列表询问包含所需要的资源但还是询问用户要不要播放 → nok。用户明确指定操作，除非无法找到对应资源并推荐其他资源，否则应该以用户的要求为主。

- nok：回答未解决用户问题
触发场景包含但不限于：「需求未闭环」、「回答内容不相关」、「回答矛盾」、「回答不完整/无结果」、「执行/操作失败」、「私域信息问题」。
强制规则：出现**回答矛盾**时，统一判定为 nok；矛盾信息会造成用户困惑，无法达成问题解决。

- need_review：信息不足，完全无法判断ok或nok，需进一步核验
need_review 分两类：
    - A）画面环境阻断（外部录制/脚本问题）：即第 1 步命中的环境类阻断场景，无法观察最终是否完成用户需求。**此类场景不写入 answer_issues。**
    - B）内容信息不足（产品侧）：仅依靠回复正文、截图无法判断应答是否解决问题；回复附带和用户查询强相关的卡片 / Super‑link，**必须点击卡片、打开链接查看详情**后，才可完成结果判定；或产品声明本机能力不支持。**此类缺陷写入 answer_issues。**
    - 示例1：用户要求创建周期性日历事件，卡片仅展示首个起始时间，无法查看后续周期配置；
    - 示例2：核验某段歌词是否对应指定歌名，卡片摘要信息不足以下定论。

「本机能力不支持」属于 B 类：写入 answer_issues，同时 problem_solved 标记 need_review，needs_review=true。
拿不准能否判定 ok / nok 的场景，优先选择 need_review。

## 第 4 步：评价原因（problem_solved_reason）
简明扼要地说明为何得出该 problem_solved。必须呼应第 2 步在 answer_issues 中查出的关键问题（或说明为何确认无问题），点出关键证据，不得与 answer_issues 矛盾。

# Part 3 — 事实冲突判定（factual_conflict，稀疏输出）
本条目是为了帮助人工筛选检查是否有信息错误而设立。
仅当用户消息中提供了「竞品答案 competitor_answer」时才做此判定，且只有判定为冲突时才在 JSON 中输出 factual_conflict: "yes"；以下情形一律**省略该字段（不输出）**：
- 用户消息未提供竞品答案；
- 产品回答与竞品答案讨论的根本不是同一件事（各说各的，无从比对）；
- 二者结论一致、互补或不矛盾。

判定标准："yes" 仅指产品回答与竞品答案在说同一件事（同一实体、同一问题点、同一数据口径），但给出的结论或关键事实完全不同、相互矛盾。
输出 "yes" 时必须**同时**输出 factual_conflict_detail：用一两句话客观转述冲突点——同一件事上产品回答说了什么、竞品答案说了什么（只转述差异，绝不判断谁对谁错）；省略 factual_conflict 的所有情形，该字段同样**省略**。
纪律：
1. 竞品答案只是另一支/另一产品给出的答案，不一定正确、更不代表标准答案——本字段只记录「是否事实冲突」，绝不判断谁对谁错；经常出现产品回答正确而竞品错误，因此绝不能因为"产品回答与竞品答案不一致"就判nok；
2. 省略该字段即视为「无冲突」。

# 人工复核（needs_review）
出现用户query和画面中用户query严重不符、产品answer_text和画面中的严重不符、画面模糊、内容被遮挡、录屏关键帧未覆盖完整回答、跨帧无法可靠去重、卡片类型或蓝字归属不确定时，needs_review=true 并说明原因。
problem_solved 出现 need_review 时，needs_review 必须为 true。
