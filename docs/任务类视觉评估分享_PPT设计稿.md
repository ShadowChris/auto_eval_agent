# 第一章：背景与需求

## 02｜助手从回答问题走向执行任务，评估对象也发生了变化

### 核心内容

```text
问答类任务：重点评价回答内容是否正确
任务类任务：重点评价真实操作是否完成
```

典型任务包括：

- 打开蓝牙、关闭免打扰；
- 设置多个闹钟；
- 导航、发送、播放、预订；
- 跨系统设置和第三方应用操作。

### 本页结论

> 当智能助手开始替用户执行操作，评估对象就从“说得对不对”变成了“事情有没有真正完成”。

> [图示占位：问答类“文字结果” → 任务类“真实执行结果”]

---

## 03｜一句“已完成”无法证明任务真的完成

### 示例

```text
Query：
打开蓝牙，关闭免打扰，并设置 4、5、6 点的闹钟

Agent 回复：
“已经为你设置完成。”
```

仍需要确认：

- 蓝牙是否真的开启；
- 免打扰是否真的关闭；
- 三个闹钟是否全部创建；
- 是否只到达中间页面；
- 是否因登录、授权或缺少信息被阻塞。

### 本页结论

> 任务类评估需要验证真实执行证据，而不能只相信 Agent 自述。

> [案例占位：Agent 回复与实际录屏结果不一致]

---

## 04｜第三方视觉是当前最通用的黑盒观测入口

### 方案对比

| 信息来源 | 优点 | 局限 |
| --- | --- | --- |
| Agent 自述 | 获取简单 | 无法证明真实执行 |
| 内部执行日志 | 过程详细 | 与被测系统强耦合 |
| 端侧状态 API | 结果直接 | 当前覆盖范围有限 |
| 第三方视觉 | 黑盒、通用、接近用户感知 | 受可见信息和抽帧影响 |

### 当前选择

- 视觉证据作为主要评估依据；
- Agent 回复用于交叉验证；
- 端侧状态未来作为补充证据；
- 人工抽样用于离线评价方案效果，不进入在线评估主流程。

> [图示占位：四种观测方式对比，突出第三方视觉]

# 第二章：整体方案设计

## 05｜系统把操作录屏转化为可复核的结构化评估结果

### 整体流程

```text
任务类 Query 数据集
→ 端侧自动执行与录屏
→ 视频校验与视觉信息预处理
→ 终端用户视觉裁判
→ 结构化评估结果
→ 汇总、回溯与导出
```

### 输入

```text
Query + Context + 操作录屏 + 可选 Agent 回复
```

### 输出

```text
完成判定 + 维度评分 + 问题类型 + 判断理由 + 视觉证据
```

### 页面说明

- 端侧自动批跑如果属于外部系统，图中应标记为“上游能力”；
- 当前已实现与规划能力使用不同颜色；
- 端侧状态辅助使用虚线表示。

# 第三章：核心模块与算法

## 06｜关键帧算法在信息完整性和模型成本之间取得平衡

### 算法路线

```text
固定频率采样 + 场景变化检测
→ 相邻时间点合并
→ UI 状态聚类与去重
→ 短暂状态、首尾画面保护
→ 帧数控制
→ 最终关键帧序列
```

### 解决的问题

- 去掉长时间重复静止画面；
- 捕获页面跳转和短暂弹窗；
- 保留任务开始、结束和最终画面；
- 当前 `max_frames=20` 是普通候选预算；首尾窗口等受保护帧强制保留时，最终可能超过 20 帧；
- 减少视觉模型输入成本。

> [图示占位：视频时间轴，上方为原始采样，下方为最终关键帧]

## 07｜终端用户裁判按目标是否闭环判断，而不是检查固定操作路径

### 当前评估流程

```text
核验录屏 Query 与输入 Query
→ 理解用户目标和生效条件
→ 阅读全部关键帧和 Agent 回复
→ 查找完成、失败、阻塞和异常证据
→ 输出结构化结论
```

### Correctness

| 结果 | 含义 |
| --- | --- |
| `ok` | 任务完整闭环 |
| `nok` | 存在可归责执行错误 |
| `no_support` | 受到客观条件阻塞 |
| `others` | 证据不足、输入或环境异常 |

### 评分维度

```text
操作完成度：70%
步骤正确性：30%
```

### 核心原则

- 不要求匹配唯一标准路径；
- 最终目标满足优先；
- 复杂任务整体判断所有生效目标；
- 当前固定使用终端用户单裁判。

# 第五章：问题与下一步

## 11｜纯视觉方案仍受到可见性和抽帧完整度限制

| 当前问题 | 具体表现 |
| --- | --- |
| 短暂信息可能漏失 | 弹窗一闪而过、状态停留时间短 |
| 小文字识别不稳定 | 系统提示、按钮和状态文字较小 |
| 后台状态不可见 | 蓝牙、闹钟等状态未必完整展示 |
| 复杂任务证据不够结构化 | 当前主要输出整题结论 |
| 视觉证据可能冲突 | 中间状态和最终状态不一致 |
| 效果验证仍需完善 | 需要建立系统化人工 Benchmark |

# PPT 制作前素材清单

## 必需素材

1. 一个任务正确完成的真实录屏案例；
2. 一个 Agent 声称完成但实际失败的案例；
3. 每个案例的关键帧和最终评估结果；
4. 当前批跑统计数据；
5. 公司模板、Logo 或期望参考的 PPT 风格。

## 建议确认项

- 主案例使用简单任务还是复杂多任务；
- 是否保留第 8 页工程能力；
- 分享时长为 10、15 还是 30 分钟；
- 成果页能够提供哪些真实数据；
- 系统设计图中如何标记外部端侧批跑能力；
- 是否需要在正文展示评估标准细节，或只放在附录。

## 建议视觉方向

- 比例：16:9；
- 风格：简洁、偏技术方案汇报；
- 主色：深蓝或深灰；
- 任务类强调色：橙色；
- 正确结果：绿色；异常与问题：红色或黄色；
- 优先使用真实手机关键帧，不使用无关装饰图片；
- 主文避免展示大段 Prompt、完整 JSON 和接口代码。
