# 任务类（录屏）抽帧算法

本文档是任务类（录屏）抽帧算法的版本基线和迭代记录。评测整体流程、裁判提示词和
Web 使用方式仍参考 `docs/操作类评测.md`；本文只描述
`src/auto_eval/media.py` 中的关键帧算法。

## 1. 当前实现版本

| 项目 | 值 |
|---|---|
| 算法版本 | `hybrid-state-v3.1.0` |
| 启用日期 | 2026-07-28 |
| 实现入口 | `extract_scene_keyframes` |
| 配置类 | `KeyframeConfig` |
| mini 数据集 | `data/test_operation_fast_query_mini.jsonl` |
| mini 数据集规模 | 17 条快系统录屏 |
| 状态 | 当前仓库实现；完整 mini 统计仍沿用下文 v3.0 历史基线 |

版本号同时写入每次抽帧生成的 `keyframes.json`，并参与 Web 抽帧缓存键计算。
修改算法版本或任务起止时间都会使旧缓存失效，避免复用不同策略生成的帧。

后续版本约定：

- 在现有算法上补充候选状态或调整兼容参数，升级次版本，例如
  `hybrid-state-v3.2.0`。
- 对状态建模或抽帧流程进行不兼容重构，升级主版本，例如
  `hybrid-state-v4.0.0`。

## 2. 输入时间语义

JSONL、Web 传递参数、抽帧函数和配置类统一使用以下字段，单位均为秒：

| 字段 | 默认值 | 含义 |
|---|---:|---|
| `task_start_time` | `7.0` | query 大致发送完成、任务开始执行的时间 |
| `task_end_time` | `null` | 显式任务结束点；为空时由算法自动推断 |

两个字段均可省略或填 `null`。显式值必须是有限的非负数字，且
`task_end_time` 必须大于 `task_start_time`，同时不能超出视频时长。
即使填写了任务结束点，算法仍会强制保留视频最终帧，用于确认任务结束后返回的界面状态。

## 3. 当前算法流程

### 3.1 生成候选帧

在任务时间窗内合并以下来源：

1. `task_start_time` 对应的任务首帧；
2. `sample_fps=1.0` 的固定频率采样帧；
3. FFmpeg `scene` 检测产生的画面变化帧；
4. 显式或自动推断的任务结束帧；
5. 距视频末尾约 0.3 秒开始尝试解码的最终帧。
6. 从任务开始起前 20 秒、任务结束前 5 秒内，每 2 秒补充一张受保护采样帧。

固定采样负责避免只依赖视频编码或场景阈值导致的漏检，`scene` 候选负责补充两次
固定采样之间的快速变化。受保护采样用于捕获顶部卡片、横幅、弹窗和开场状态等局部变化；
它采用更严格的去重阈值，只有画面高度一致时才会合并。

### 3.2 合并相邻时间点

时间差不超过 `timestamp_merge_gap_s=0.25` 的候选视为同一事件，优先保留任务首帧、
任务结束帧和 scene 帧，减少同一次界面跳变产生的近重复帧。

### 3.3 UI 状态聚类

每张候选帧会经过高斯模糊并缩小为 `16×27` 的灰度布局特征。相邻帧的布局距离达到
`state_layout_threshold=0.05` 时划分为新的 UI 状态。

对于持续时间达到 `stable_min_duration_s=1.5` 的状态，保留能够表示状态开始或结束的
候选帧。该步骤用于合并同一界面中的光标、计时器、轻微文字变化和录屏计时变化。

### 3.4 短暂弹窗保护

对 A → B → A 型局部变化进行额外保护。当 B 持续时间不超过
`transient_max_duration_s=4.0`，且变化面积、返回相似度满足阈值时，B 会标记为
`transient-local-A-B-A`，避免静音、24 小时制等短暂卡片被状态去重吞掉。

### 3.5 自动任务结束点

未填写 `task_end_time` 时，算法比较候选状态与最终智能助手外壳的相似度，结合最终状态
稳定时长和置信度推断任务结束点。推断成功的帧标记为 `task-end-auto`；置信度不足时
不强行截断任务区间。

### 3.6 帧数预算和最终严格去重

普通候选以 `max_frames=20` 为目标预算。任务首尾、任务结束、短暂 A-B-A 状态和
`source=protected-*` 的受保护采样属于强制保留项；当这些强制项本身超过 20 张时，当前
实现不会再次裁剪，因此最终帧数可能大于 20。`max_frames` 目前不是严格上限。

最终去重使用清晰图像特征，而不是模糊布局特征：

- RMS 阈值：`final_dedup_rms_threshold=0.008`
- 变化像素占比阈值：`final_dedup_changed_fraction_threshold=0.01`

任务结束帧和视频最终帧属于保护帧。视频最终帧始终保留，即使它与前一帧相似。
受保护采样使用独立的更严格阈值 `protected_sample_dedup_rms=0.002` 和
`protected_sample_dedup_cf=0.002`。

## 4. 主要默认参数

| 参数 | 默认值 | 调大后的主要效果 |
|---|---:|---|
| `max_frames` | 20 | 增加普通候选预算；不能限制强制保留帧总数 |
| `sample_fps` | 1.0 | 更容易捕获短变化，同时增加候选计算量 |
| `scene_threshold` | 0.06 | scene 候选更少，更容易漏掉小变化 |
| `scene_min_gap_s` | 0.8 | 合并更多相邻 scene 事件 |
| `timestamp_merge_gap_s` | 0.25 | 合并更多时间接近的候选 |
| `state_layout_threshold` | 0.05 | UI 状态更难被划分，输出帧更少 |
| `stable_min_duration_s` | 1.5 | 更少保留短状态 |
| `transient_max_duration_s` | 4.0 | 允许保护持续更久的 A-B-A 弹窗 |
| `auto_task_end_confidence_threshold` | 0.60 | 自动任务结束判断更保守 |
| `final_dedup_rms_threshold` | 0.008 | 最终去重更激进 |
| `final_dedup_changed_fraction_threshold` | 0.01 | 最终去重更激进 |
| `protected_sample_interval` | 2.0 | 受保护采样更稀疏 |
| `protected_begin_window` | 20.0 | 扩大任务开头的受保护采样窗口 |
| `protected_end_window` | 5.0 | 扩大任务结尾的受保护采样窗口 |

完整配置及其默认值以 `KeyframeConfig` 为准。调整参数时必须重跑 mini 数据集，不应只针对
单个案例调参。

2026-07-23 使用当时的 v3.0.0 实现完整重跑 17 条 mini 数据。以下结果用于历史对照，
不能代表当前 v3.1.0 的帧数分布：

| 指标 | 结果 |
|---|---:|
| 成功案例 | 17/17 |
| 抽帧异常或空结果 | 0 |
| 总帧数 | 72 |
| 单案例帧数范围 | 2–8 |
| 平均帧数 | 4.24 |
| 保留任务首帧 | 17/17 |
| 保留视频最终帧 | 17/17 |

重点案例结果：

- `fast_query_4`：保留静音模式卡片；
- `fast_query_5`：保留 24 小时制卡片；
- `fast_query_7`：保留相机准备、拍照界面、任务结束和视频最终状态；
- `fast_query_28`：保留录像开始、录像进行中、任务结束和视频最终状态；
- `fast_query_55/73/104`：长视频均保留实际应用界面、自动任务结束帧和最终助手界面。


其中 `regression_summary.json` 保存逐案例时长、抽帧时间、保留原因、自动任务结束置信度和

## 6. v3.1.0 变更与当前注意事项

### 6.1 v3.0.0 的已知问题

v3.0.0 的 mini 回测中有 3 条明确案例：

| 案例 | v3.0.0 结果 | 漏掉的信息 |
|---|---|---|
| `fast_query_30` | 7.0、10.0、96.125 秒，共 3 帧 | 约 18–82 秒持续显示的顶部操作卡片 |
| `fast_query_34` | 7.0、51.561 秒，共 2 帧 | 约 14–39 秒持续显示的字体设置卡片 |
| `fast_query_95` | 7.0、9.0、56.446 秒，共 3 帧 | 约 14–44 秒持续显示的卡 2 操作卡片 |

根因：

1. 卡片主要改变助手界面的局部区域；
2. 布局特征经过高斯模糊并缩小为 `16×27` 后，对局部卡片不够敏感；
3. `fast_query_34` 的最大相邻布局距离约为 `0.0475`，低于 v3.0.0 的 `0.05` 阈值，整段被
   聚成一个状态；
4. 这些卡片持续时间大于 4 秒，不符合短暂 A-B-A 弹窗保护条件；
5. 它们在状态聚类阶段就没有进入最终候选，因此问题不在最终严格去重。

### 6.2 已落地的优化

v3.1.0 没有直接降低全局 `state_layout_threshold`，而是增加受保护采样：

1. 任务开始后的前 20 秒每 2 秒补充一帧；
2. 任务结束前 5 秒每 2 秒补充一帧；
3. 对受保护帧采用更严格的相似去重，减少局部卡片被普通状态聚类吞掉的概率；
4. 默认候选预算从 16 提高到 20。

自动化测试覆盖了任务开始 18～20 秒出现的局部弹窗，确保扩大后的开头窗口能够保留该状态。

### 6.3 当前限制

- 受保护采样优先保证信息覆盖，但会弱化帧数控制。长录屏或局部变化频繁时，最终帧数可能
  超过 20；曾出现 34 帧属于这一实现语义，不是 `max_frames` 配置未读取。
- 如需严格控制模型视觉输入成本，应后续为强制保留项增加二次选帧或单独的硬上限，并在
  修改后重跑 mini 与大批数据回归。
- 当前尚未在本文登记 v3.1.0 的完整 17 条 mini 回测统计；在补齐前，不应继续引用
  v3.0.0 的“2–8 帧、平均 4.24 帧”描述当前版本。

下一次算法调整仍需重点回归 `fast_query_30/34/95`，同时确保
`fast_query_4/5/7/28` 已保留的关键状态不回退，并记录逐案例帧数和时间点差异。

## 7. 测试与回归入口

- `tests/test_media.py`：算法配置、严格去重和真实 FFmpeg 视频集成测试；
- `tests/test_operation_import.py`：JSONL 时间字段、参数透传、缓存失效和视频时长校验；
- `data/test_operation_fast_query_mini.jsonl`：快速人工回归数据集；
- 每次抽帧目录中的 `keyframes.json`：逐案例算法版本、参数、抽帧时间和保留原因。

版本升级时，应先更新实现和测试，再完整重跑 mini 数据集，最后把结果追加到本文档，保留
旧版本基线，不覆盖历史数据。
