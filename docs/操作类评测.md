# auto_eval_agent · 任务类（录屏）评测

> 最后更新：2026-09-10。当前运行模式为 `mode=operation`，默认固定使用**终端用户单裁判**。评测语义以 `config/skills/operation.yaml` 为准，人类可读规则见[任务类评估标准](任务类评估标准.md)；抽帧参数与回归基线见[任务类抽帧算法](操作类抽帧算法.md)。

## 一、当前流程

```text
手工录入或导入 JSONL / CSV / Excel
  → 解析、校验并预览待评数据
  → 按题解析视频路径并提取关键帧
  → 终端用户视觉裁判联合 Query、用户图片、关键帧和 Agent 自述判断
  → 输出 correctness、issue_types、维度评分和证据理由
  → SSE 实时展示，并写入历史、统计、报告和导出文件
```

任务类不运行多裁判投票或主席仲裁。底层仍复用通用 `JudgeClient`、调用日志和输出解析能力；Web 中切换 Provider 或模型只替换模型服务，不改变“终端用户”裁判身份。

## 二、输入与路径

JSONL 每行一题，例如：

```jsonl
{"id":"op_alarm_001","query":"设置明天早上7点的闹钟","context":"设备时区为北京时间","video_path":"data/videos/alarm.mp4","answer":"已设置完成","task_start_time":7}
```

| 字段 | 必填 | 说明 |
|---|---:|---|
| `id` | 否 | 稳定题号；追加数据时建议提供，且批次内不可重复 |
| `query` / `question` | 是 | 用户操作意图 |
| `video_path` | 是 | 录屏路径 |
| `context` | 否 | 时间、地点、设备状态等可信背景；任务类不会自动注入当前时间 |
| `answer` / `agent_statement` | 否 | Agent 最终回复，用于与画面交叉验证 |
| `query_images` | 否 | 用户原始输入图片路径或 HTTP/HTTPS 链接数组，最多 4 张；不能单独作为完成证据 |
| `query_image_path` / `attachment_path` | 否 | 单图路径或 HTTP/HTTPS 链接；没有非空 `query_images` 时按此顺序读取 |
| `task_start_time` / `task_end_time` | 否 | 执行区间秒数；开始默认 7 秒，结束为空时自动推断 |

Web 支持 `.jsonl`、`.csv`、`.xlsx`、`.xlsm` 和 `.xls` 数据集。导入只解析字段并生成统一预览，可取消勾选不需要评估的题；真正的视频校验和抽帧在“开始评估”后进行，单题失败不阻塞同批其他题。

相对 `video_path` 会在项目根目录和 `OPERATION_VIDEO_ROOTS` 配置的外部根目录中解析。唯一命中时使用该文件；多处同名命中会报歧义，需填写更完整的相对路径或受信目录内的绝对路径。macOS/Linux 多目录用 `:` 分隔，Windows 用 `;` 分隔。

用户图片支持本地路径和普通 HTTP/HTTPS 图片直链，不要求 OBS。按可信用户场景直接读取，
不设域名白名单或内网地址限制；支持重定向和带参数链接。每张仍限制 10MB、2500 万像素，
只接受可解码的 JPEG/PNG/WEBP。网络操作设置 10 秒连接、30 秒读取超时，接收图片块时检查
60 秒总时长预算；超时、HTTP 错误或返回非图片内容会使该题失败，不忽略图片继续评估。
导入只解析链接，开始准备评估输入时才下载，保存在 `runs/uploads/query_images/remote/`。
原始字段和 `source_data` 保留 URL，运行时 `query_images` 使用本地副本，便于模型输入及历史预览。
重新导入同一链接会重新下载；已准备的本地副本在重跑时复用。录屏下载和评估标准均不改变。

## 三、视觉信息预处理

### 多轮输入与逐行输出

旧的单轮 JSONL、CSV、Excel 和 API 调用保持兼容。多轮文件按原始行序连续排列，
`is_start/is_end` 支持 TRUE/FALSE、1/0：首轮 TRUE/FALSE，中间 FALSE/FALSE，
末轮 FALSE/TRUE，独立单轮 TRUE/TRUE；两列均未提供仍按旧单轮处理。
批量导入按局部隔离处理，不因一个异常会话拒绝整份数据，也不静默丢轮：

- 缺少结束标记时，遇到下一条明确的 `is_start=TRUE` 或文件末尾，按已有轮次结束并展示警告，不跨越新的开始标记合并。
- 无对应开始标记的续轮、非法标记、损坏的 JSON 行保留为失败行。会话中途出现这类行时，其后依赖该历史的轮次也失败；到下一条明确开始标记后恢复正常归组。
- 时间、图片或内部历史前缀无效时，之前有效的轮次仍可评估，异常轮及依赖它的后续轮次失败；不会跳过异常历史后拼接后轮。
- 失败行在预览、历史记录、进度和导出中保留，`error` 记录原因，`correctness` 留空；可选择重跑，输入错误须先修正对应输入。重复 id 的条目会以临时执行 id 保留为失败行，原 id 保留在原始字段中，不覆盖其他结果。

多轮每轮必须提供 `query`、`task_start_time`、`task_end_time`。时间是相对完整视频起点的秒数，
必须非负、结束大于开始且不与前轮重叠；不能沿用每轮默认 7 秒。完整 `video_path` 可以在会话任一轮提供，
其他轮可以为空，非空必须一致；首轮为空时复用本会话唯一录屏并提示警告。全部缺失、存在冲突录屏或视频不可读取时，仅该会话失败。
超出视频时长的多轮时间窗使该轮及依赖它的后轮准备失败，
不回退为整段视频，以免将其他轮证据错误绑定。单轮原有时间回退策略不变。
文件会话只按连续行的 `is_start/is_end` 分组，不用业务 `case_id` 分组或校验。原始 `case_id` 可以逐行不同、为空或跨会话重复，原样保留。系统自动维护独立的 `conversation_id`（优先用会话首行 id，否则生成），每轮使用自己的唯一 id（未提供时生成），原始附加列保留。

例如：

```jsonl
{"id":"alarm_1","query":"帮我设一个闹钟","answer":"请问几点？","video_path":"data/alarm.mp4","is_start":true,"is_end":false,"task_start_time":0,"task_end_time":8}
{"id":"alarm_2","query":"明早七点","answer":"已设置","video_path":"","is_start":false,"is_end":true,"task_start_time":10,"task_end_time":20}
```

API 继续使用 `/api/eval` 的 `items`，既可传上述连续标记行，也可传一条
`{id, video_path, turns: [{query, answer?, context?, query_images?, task_start_time, task_end_time}, ...]}`。
批量结构化 turns 展开为每轮一个 Case。单题接口支持相同结构，但只评所给前缀的最后一轮，外层 id 是该次结果 id。
图片按轮绑定，仍支持 attachment_path 和网络直链。导入逐轮预检并生成每轮可独立勾选的预览；即使只选后轮，也保留它的历史前缀。追加、重跑、进度、统计和报告均以每个 Query/轮次计数，不做会话整体统计。
`turns`、`turn_index`、`turn_count`、`conversation_id` 是系统维护的内部会话字段；表格/JSONL 原始连续行只需 `is_start/is_end`，不要求上游生成这些内部字段。显式 API 前缀仍会校验这些字段，批跑时异常局部记录为失败，不变成整批必填字段错误。
只修改某个历史轮次的输入而不更新后轮前缀时会拒绝合并，防止同一会话出现冲突历史；请同步替换受影响轮次，或新建评估集。独立重跑不改输入时不受影响。

例如上述闹钟会话：首轮合理等待时间参数为 no_support；第二轮继承“设置闹钟”的要求，只有实际设好七点才为 ok，而不是因为用户回答了时间就自动 ok。首轮结果保持不变。历史错误后被当前轮成功纠正，可以是 nok → ok；一个历史独立任务失败，不会自动把后续新任务也判错。
单轮保持原有 Prompt 规则内容、顺序和渲染形式，多轮条件分支只在含 turns 时注入；回归测试固定了改动前单轮模板的渲染摘要，防止组合改造无意改变原链路。

分轮复用现有抽帧算法，每轮普通候选预算为 20 帧，保留原算法的受保护证据（不是硬上限）。
多轮先按时间窗裁切临时视频再抽帧，避免结束点 seek 跳到下一轮；元数据恢复完整录屏的绝对时间，临时片段随即删除。单轮算法不变。
逐轮模式复用帧时也会校验时间窗策略版本，拒绝可能串入后轮画面的旧策略帧；历史查看与导出不受影响，需重新抽帧后才可重新评估。
本地相同视频与时间窗缓存共享抽帧，避免每个前缀重复抽取历史轮次；远程视频仍沿用现有下载生命周期。
每个结果只包含截至当前轮的帧，不跨轮删除相同状态。全局帧号按绝对时间排序，keyframes.json 保存每帧 turn_index/time。
历史文本、Answer、图片同样只提供前缀；长会话的模型输入会随历史增长。

Excel 的“评估结果”“逐题结果”“数据集明细”逐行对应输入，每轮保留原始 Query、Answer、
Context、图片、时间和相关原始列；每轮都有评估字段。保留原始业务 case_id，增加 conversation_id、turn_index、
turn_count、evaluation_scope=latest_turn 标识。JSONL 导出每轮独立 evaluation 和所需 turns 前缀。
失败子集脚本只选择失败轮次，但携带其历史前缀，可独立重跑；旧整会话导出的兼容逻辑保留。
单轮导出字段顺序保持不变，混合数据集增加会话标识。

旧历史任务若冻结了不支持多轮或整会话口径的规则快照，追加逐轮多轮会明确拒绝并提示新建评估集，
不会静默套用旧单轮 Prompt 或修改历史规则；向旧任务追加单轮不受影响。
旧整会话历史直接复用帧创建“逐轮新标准版本”也会在创建前拒绝；需重新导入原始行，按各轮前缀重新抽帧。旧历史本身的查看、导出和按原快照重跑仍保留。

多组联合裁判尚不直接拼多轮 Prompt：包含多轮的组会回退逐组独立评估，按每组当前轮承接要求判断。

当前实现版本为 `hybrid-state-v3.2.0`：在任务时间窗内合并 1 FPS 固定采样、FFmpeg scene 变化帧、任务起止帧和首尾窗口受保护采样，再经过时间合并、UI 状态聚类、短暂弹窗保护和严格图像去重。提供有效 `task_end_time` 时不取整段视频的末帧；未提供时仍用末帧辅助推断结束点并保留。`max_frames=20` 是普通候选的目标预算，不是硬上限；受保护帧可能使最终帧数超过 20。

抽帧结果保存在 `runs/videos/imported/<session>/<item>/`，`keyframes.json` 记录算法版本、参数、时间戳和保留原因。算法版本或任务起止时间变化会使缓存失效。实现入口为 `src/auto_eval/media.py::extract_scene_keyframes`。

## 四、裁判与输出

`RubricJudge.score(..., eval_mode="operation")` 将以下内容组成一次多模态评估：

- 原始 Query、可选 Context 和 Agent 自述；
- 可选用户输入图片；
- 按时间顺序排列的录屏关键帧；
- `operation.yaml` 中的证据规则、判定优先级、问题类型和评分锚点；
- `config/knowledge/operation.yaml` 中已发布的产品事实。

主要输出包括：

| 字段 | 含义 |
|---|---|
| `correctness` | `ok`、`nok`、`no_support`、`others` 四分类闭环结论 |
| `issue_types` | 受控问题类型数组；非 `ok` 时首项为决定整体结论的主要根因 |
| `task_type` | 模型按可独立验收结果数量判断 `simple` / `complex` |
| `rubric` / `rubric_reasons` | “操作完成度”“步骤正确性”的分数与理由；证据不足时可为 `null` |
| `is_low_level` | 是否属于用户感知明显、可稳定避免的低级问题 |
| `evidence_frames` / `rationale` | 录屏证据帧和最终理由 |

结果页会单独展示 Agent 自述。任务类主裁判已停止生成执行链路判断；历史和导出中的链路字段仅用于兼容旧结果。

## 五、Provider、并发与限速

评估配置可选择 OpenAI 兼容 Provider、模型和模型请求限速。选择“跟随裁判角色默认配置”时使用 `config/judges.yaml` 中终端用户裁判的连接；选择自定义 Provider 时，本批任务改用所选模型，但仍执行终端用户 Prompt。

- 默认任务并发为 8；并发控制同时在途的题目数。
- 默认请求限速为每 1 秒最多 9 次，可按批次或重跑调整；限速器按 Provider/API 作用域在当前服务进程内共享，并平滑发放请求。
- Provider 配置位于忽略目录 `runs/web_settings/`。API Key 加密保存且不进入历史、导出或调用日志；部署时建议通过 `.env` 固定 `AUTO_EVAL_CREDENTIAL_KEY`。
- 历史快照会记录无密钥的 Provider、模型、配置版本和限速参数，便于回溯。

## 六、历史追加与数据集修订

任务类历史记录支持“追加到历史评估集”。`POST /api/eval` 使用 `submit_mode="append"` 和目标 `task_id`；系统以 `index`、`序号` 或 `id` 等稳定标识检查重复项，并先返回合并预览。重复题可保留旧结果，或用新输入覆盖并仅重跑该题；Query 不一致时必须人工选择。

数据集维护页提供：

- 排除或恢复单题；排除项保留在历史中，但不参与统计和默认导出；
- 下载每次初始或追加批次的原始 JSONL 快照；
- 从最新有效追加批次开始回滚。新增题会被排除，被覆盖题会恢复到追加前版本；初始批次不可回滚。

相关接口：

```text
GET  /api/eval/{task_id}/dataset
POST /api/eval/{task_id}/dataset/items/exclude
POST /api/eval/{task_id}/dataset/items/restore
POST /api/eval/{task_id}/dataset/batches/{batch_id}/rollback
GET  /api/eval/{task_id}/dataset/batches/{batch_id}/export
```

普通任务类单批支持追加与修订；“任务类多组评估（Beta）”不支持这些操作。

## 七、统计、对比与导出

- `GET /api/eval/{task_id}/statistics`：三分类分布、OK/NOK 率、覆盖率，以及分开的效果问题 `issue_types` 和复核类别 `need_review_cate` 统计。OK/NOK 率及 Issue Type 占比以 `ok + nok` 为分母；判定分布和复核类别占比以全部有效判定为分母。各类在同一 Case 内去重，多标签占比可超过 100%。
- 对比分析和 Excel/HTML 报告分别展示“效果问题对比”和“需复核类别对比”。效果问题在选定的共同有效集合中，分别以各组 `ok + nok` 为分母；复核类别始终以对应双方共同有效 Case（含 `no_support`）为分母，不随“均为 OK/NOK”效果口径过滤。复核原因增减不代表效果优化或劣化，可点击类别查看对应 Case。
- Web 与离线 HTML 的右侧类别分析共用一个模块，通过“效果问题 / 需复核类别”Tab 切换，复用柱状图、雷达图、表格、排序及下方 Case 列表；切换时清除上一类筛选。复核变化采用中性蓝灰配色，不标记优化/劣化，统计分母不变。Excel 仍以两个独立子表导出。
- 上传已评估 JSONL/CSV/Excel 支持顶层或 `evaluation` 内的 `need_review_cate`，以及中文列“需复核类别”；历史 `others` 兼容合并为 `no_support`，旧复核原因从 `issue_types` 分离。只做读取兼容，不重写历史快照。Excel 对比导出包含独立“需复核类别对比”子表和逐题横向复核字段。
- `GET /api/eval/{task_id}/report`：单批交互报告数据。
- `GET /api/eval/{task_id}/export`：导出 CSV、JSON、JSONL、XLSX、HTML 或关键帧压缩包。
- 普通任务类 XLSX 首个子表为面向用户的“评估结果”；“逐题结果”保留完整技术字段，“数据集明细”保留原始输入字段。
- `POST /api/operation/comparison/analyze`：混合历史结果和上传结果，对比 2～5 组数据。
- `POST /api/operation/comparison/export`：导出对比 XLSX 或离线 HTML。
- `POST /api/eval/single`、`GET /api/eval/single`：按外部 `task_id + item.id` 写入并查询单题，详见[任务类单题评测接口](任务类单题评测接口.md)。

SSE 入口为 `GET /api/eval/{task_id}/stream`。历史和裁判调用明细分别保存在 `runs/web_history/` 与 `runs/judge_calls/YYYY-MM-DD/{task_id}/`。

批跑接口、历史详情及 Web 历史记录统一使用以下任务级状态。进度只统计成功生成评估结果的题目，`processed` 同时包含成功和逐题失败的题目：

| `status` | 含义 | 判定口径 |
| --- | --- | --- |
| `running` | 进行中 | 初始批跑、追加评估或重跑仍在执行 |
| `completed` | 完成 | 成功进度为 `n/n` |
| `partial_completed` | 部分完成 | 执行终止且成功进度为 `m/n`，其中 `0 < m < n` |
| `failed` | 失败 | 执行终止且成功进度为 `0/n` |
| `cancelled` | 取消 | 用户手动中断初始批跑或追加评估 |

模型服务下拉框支持将当前 Provider 与 Model 保存为系统默认。默认绑定保存在 `runs/web_settings/llm_default.json`，不包含 API Key；服务重启后 Web 会自动恢复该选择。`POST /api/eval`、`POST /api/eval/single` 和重跑接口未显式传入 `judge_backend` 时使用该默认绑定，显式传入时请求参数优先。清除默认绑定后恢复使用角色/YAML 配置。

### 裁判原生思考日志

结果行的 `judge_calls` 下载包含原生思考说明；任务级原始日志仍位于
`runs/judge_calls/YYYY-MM-DD/{task_id}/judge_calls.jsonl`。
修改代码后需重启服务，新调用才会保存服务端返回的思考原文；不改变模型思考开关或评判规则。

| 字段 | 说明 |
| --- | --- |
| `llm_rounds[].reasoning_content` | 本轮接口返回的原生思考文本，与正文 `content` 分开保存，不混入 JSON 判定或正文回调。 |
| `llm_rounds[].thinking.request_mode` | `provider_default`：请求未指定开关；`enabled` / `disabled`：请求显式指定；`unknown`：旧记录没有请求信息。 |
| `llm_rounds[].thinking.status` | `confirmed`：有原生思考文本或正数思考 Token；`unconfirmed`：没有足够返回证据，不能等同于关闭。 |
| `llm_rounds[].thinking.reasoning_tokens` | 服务端报告的本轮思考 Token；未返回为 `null`。 |
| `llm_rounds[].thinking.content_status` | `recorded`：已保存非空思考原文；`not_returned`：新调用未返回原文；`not_recorded`：旧日志没有记录原文。 |
| `thinking_summary` | 调用记录及单题下载中的汇总，包含确认思考的轮数、已知思考 Token 合计、报告用量轮数和原文记录轮数。未报告的用量不按 0 估算。 |

普通运行日志仅展示“原生思考”“思考Token”“原生思考字符”等摘要，不打印思考原文。
正文中的 `<analysis>...</analysis>` 是按 prompt 输出的评判分析，不能据此确认模型原生思考。
旧历史下载时补充说明，不修改原日志；已有正数 `reasoning_tokens` 的旧记录可确认思考，
但不能恢复当时未保存的原文。模型或代理未返回的思考内容同样无法记录。

## 八、已知限制与验证

- 评估只依据采样到的可见证据；极短瞬态、遮挡、模糊画面或录屏外状态可能无法判断。
- `OPERATION_VIDEO_ROOTS` 是路径访问边界，不会把任意外部路径自动视为可信。
- 请求限速是单进程内共享；多进程或多实例部署需要在外层继续做全局限流。
- 当前端侧前后状态采集与视觉结果融合仍处于规划阶段，尚未进入运行链路。

常用验证命令：

```bash
python -m pytest -q tests/test_operation_import.py tests/test_web_append.py \
  tests/test_web_dataset_revision.py tests/test_web_llm_providers.py
```

启动评估台：`python -m auto_eval.web.server`，浏览器访问 `http://localhost:8502`。
